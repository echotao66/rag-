## 项目经历

### Cortex · 透明 AI 助手（个人项目）

技术栈：Python / FastAPI / SSE / numpy / DeepSeek / MCP SDK / Docker · Docker Compose / Caddy / pytest / 原生 HTML·JS

项目简介：一个可观察的 AI Agent，把记忆、工具调用、MCP、前后端串成完整链路，Agent 每一步决策（回忆 / 调工具 / 固化事实）均以事件流实时可视化；Agent 核心循环手写（仅 LLM 客户端接入 LangChain 官方 DeepSeek 集成）；已容器化并部署到云服务器，公网可访问。

- **双通道记忆系统**：针对 LLM 无状态、跨对话遗忘的问题，用 numpy 手写 `VectorMemory`「余弦相似度 × 指数时间衰减」+ `FactStore` 三元组冲突合并 + LLM 固化对话为事实/摘要，实现跨会话记忆检索与自动更新。
- **可靠工具调用**：针对裸调 function calling 乱猜参数的问题，基于 `@tool` 装饰器统一工具抽象 + 手写 JSON Schema 校验 + 失败回填重试 + 幂等结果缓存，实现 ReAct 多轮循环。
- **安全边界**：针对 LLM 调用系统能力的破坏面，通过命令白名单 + 危险片段黑名单 + 路径越界检查三重拦截，计算器用 `ast` 白名单运算符替代 `eval`。
- **MCP 协议集成**：针对 MCP 为 async 协议而主循环同步的矛盾，用「后台 event loop + 常驻协程」桥接自写文件系统 MCP server（stdio），实现跨进程工具标准化接入。
- **透明可观测**：结构化事件流 + FastAPI SSE 实时推送 + 原生三列前端，实时可视化完整推理链；脚本化 LLM 单测离线跑通全链路。
- **容器化与云上部署**：针对「本机 Python 3.14 能跑、Linux 服务器上 chromadb / onnxruntime 没有对应 wheel 装不上」的交付问题，用 Docker 固化运行环境（`python:3.12-slim` 基础镜像 + 依赖清单前置以命中分层缓存 + 非 root uid 10001 运行），并以 Docker Compose 编排双容器：Caddy 独占公网端口做反代与 Basic 鉴权，cortex 仅 `expose` 不发布端口、公网无法直连；记忆 bind mount 落盘宿主机，容器重建不丢。鉴权刻意放在反代而非应用代码里，后续上域名 + HTTPS 只需改 Caddyfile 几行、应用侧零改动；对外仅开 1 个端口。
- **沙箱漏洞自查与修复**：部署前自查发现 `read_file` 沙箱**只校验「路径未越界」**，而工作目录就是项目根、`.env` 恰在其中——公网上任何人对 Agent 说一句「读一下 .env」即可拿到 API key，且会作为 `tool_result` 事件渲染到前端。修法是补一层**按文件名**的敏感名单（`.env*` / `*.key` / `*.pem` / `id_rsa`…，按名字而非按目录匹配，因此「让 Agent 读自己代码」的演示不受影响）。修复过程中还推翻两个「看起来显然、实测不成立」的假设：MCP 同名工具会**覆盖**内置工具（线上实际跑的是 MCP 版 `read_file`，内置那份是死代码 → 两个入口必须共用同一套沙箱函数，否则修一个另一个还漏着）；mcp SDK 传给子进程的是**过滤过的环境变量白名单**而非完整 `os.environ`（沙箱根必须显式 `env=` 注入）。定位为纵深防御第二层——第一层是 `.env` 根本不进镜像（`.dockerignore` + 密钥走环境变量注入）。

### 私有知识库问答助手 · RAG（个人项目）

技术栈：Python / numpy / FastAPI / SSE / DeepSeek / sentence-transformers / pytest / 原生 HTML·JS

项目简介：一个从零手写的本地知识库问答应用，把文档喂进去后用自然语言提问，检索相关片段并流式生成带引用出处的回答，减少大模型胡编；核心链路（分词 / 检索 / 融合 / 引用）手写、不依赖 LangChain，自带 Web 前后端。

- **混合检索与 RRF 融合**：针对纯向量对专有名词、精确编号易漏、纯关键词对口语化改写易漏的问题，手写 BM25（IDF + k1/b 平滑 + 中英文分词）与 dense 语义向量双路召回，用 RRF 倒数排名融合、量纲无关；自建 50 篇文档 / 42 条 query 评测集实测 hybrid recall@3 78.0%、MRR@5 0.858，均高于 dense 与 BM25 单路（各 72.0% / 0.778、0.782）。
- **多轮对话与查询改写**：针对「那第二个呢」这类残缺追问直接检索会召回错的问题，用 LLM 把历史 + 当前问题改写成独立检索 query 再检索，实现多轮追问不跑偏。
- **引用可控与流式生成**：针对 LLM 回答无依据、无出处的问题，将命中片段按 `[n]` 编号注入 prompt 约束带引用回答并解析回显；用 OpenAI 兼容 stream 逐 token 推送，SSE 实现打字机效果。
- **文档摄取与持久化**：针对知识库持续增长、重复导入浪费的问题，用内容 SHA-256 做 doc_id 去重、增量摄取；chunk 向量 JSON 落盘，重启恢复文档与 ID 计数。
- **可插拔与可观测**：针对默认零依赖、生产要换真模型 / 向量库的矛盾，把 embedder / 分块 / 重排 / 存储四处抽成协议接口；检索来源、改写 query、引用编号以事件流全程可视化（FastAPI SSE + 原生前端），并自建 recall@k 评测脚本量化验证。

**项目成果 · 实测数据（`python tests/benchmark.py`，50 篇文档 / 42 条 query，语义 embedder）**

| 指标 | dense（向量） | sparse（BM25） | hybrid（RRF） |
|------|--------------|----------------|---------------|
| recall@1 | 58.0% | 60.0% | **66.0%** |
| recall@3 | 72.0% | 72.0% | **78.0%** |
| recall@5 | 84.0% | 74.0% | **84.0%** |
| MRR@5 | 0.778 | 0.782 | **0.858** |
| nDCG@5 | 0.786 | 0.773 | **0.851** |
| 单条 query 平均耗时（墙钟单次运行，有波动） | ~13 ms | **~0.3 ms** | ~13 ms |

分类别看，两路互补关系很清楚（recall@3）：

| 类别 | 条数 | dense | sparse | hybrid |
|------|------|-------|--------|--------|
| 英文精确关键词 | 10 | 80.0% | 90.0% | **100.0%** |
| 英文近义改写 | 15 | **93.3%** | 73.3% | **93.3%** |
| 中文精确 | 6 | 100.0% | 100.0% | 100.0% |
| 中文改写 | 6 | 66.7% | **100.0%** | 83.3% |
| 英文多相关（一题 2~4 篇） | 5 | 30.8% | 30.8% | 30.8% |

- **RRF 的价值被量化到「补齐单路短板」**：英文精确关键词上 hybrid 100%，把 dense 的 80%、BM25 的 90% 都补满；英文改写上保住 93.3%，而 BM25 掉到 73.3%。
- **实测推翻了一个我自己先写进简历的假设**：RRF **并非「永不劣于任一单路」**——中文改写类上 hybrid 83.3% 低于纯 BM25 的 100%（融合时被 dense 那一路的低排名结果拉偏）。这条已从简历里删掉，改成如实陈述。
- **已知短板**：一题多相关文档时三路都只有 30.8%，单向量 / 单关键词对「一题多答案」本就吃力，改进方向是 multi-query 扩展（未做）。

**项目成果 · 多轮查询改写（`python tests/benchmark_rewrite.py`，10 组残缺追问，真实 DeepSeek API）**

- 直接检索残缺追问 recall@3 = 40.0%，LLM 改写后再检索 = 42.5%（2 组改善 / 7 组持平 / 1 组变差）——**改写收益在本评测集上并不显著**，如实记录而不是挑有利样本。
- 但该评测跑出一个真问题：改写器会把英文追问改写成中文，而知识库以英文文档为主，跨语言召回直接归零（10 组里 4 组）。已在 prompt 里加语言约束，**只缓解未根治**（加约束后仍有 4 组漂移），可靠做法是代码里校验返回语言、不一致就退回原 query，列为已知未修项。

### 面试前自查（这些点都可能被追问，先背熟）

1. **RRF 为什么不用直接加权相加**：两路得分量纲不同（余弦 [-1,1]、BM25 正实数），RRF 只关心排名、量纲无关。
2. **HashEmbedder 为什么用 crc32 不用 hash()**：内置 hash() 每进程随机化，落盘后跨进程向量不一致。
3. **hybrid 到底强在哪、以及它并不总是最强**（这题会被追问，别背旧版）：50 篇 / 42 query 实测 hybrid recall@3 78.0% vs dense 72.0% / BM25 72.0%，MRR@5 0.858 vs 0.778 / 0.782。分类别看价值才清楚——英文精确关键词上 hybrid 100% 补满了 dense 的 80% 和 BM25 的 90%，英文改写上保住 93.3%（BM25 只有 73.3%）。**但不要说「RRF 永不劣于任一单路」**：中文改写类上 hybrid 83.3% 反而低于纯 BM25 的 100%，因为 RRF 会把 dense 那一路的低排名结果也计进总分。这个假设是我自己先写进简历、又被实测推翻的，如实讲反而是加分项。
4. **MCP 为什么走协议而不是直接 import**：工具跨语言、跨进程、标准化；async/sync 桥接用「后台 event loop + 常驻协程」。
5. **多轮 RAG 为什么先改写再检索 —— 以及实测收益其实不显著**：机制上残缺追问（「那第二个呢」）缺上下文、直接检索会召回错，所以先用 LLM 补全成独立 query。但 10 组残缺追问实测下来 recall@3 只从 40.0% 到 42.5%（2 组改善 / 7 组持平 / 1 组变差），**收益不显著**，别把它讲成银弹。这个评测真正的价值是挖出改写器的语言漂移：它会把英文追问改写成中文，跨语言召回直接归零（10 组里 4 组），加 prompt 约束只缓解未根治。
6. **文档摄取怎么去重**：内容 SHA-256 做 doc_id，同内容同 id，重复导入直接跳过，实现增量。
7. **沙箱漏洞是怎么发现和修的**（部署前自查的重点）：`read_file` 原本只校验「路径没越界」，而工作目录就是项目根、`.env` 正在里面 → 公网上说一句「读一下 .env」就能拿到 API key，还会渲染到前端。修法是补一层**按文件名**的敏感名单（按名不按目录，所以不影响「让 Agent 读自己的代码」的演示）。关键在**讲清纵深防御的层次**：第一层是 `.env` 根本不进镜像（`.dockerignore` + 密钥走环境变量注入），黑名单只是兜底的第二层——「结构隔离才是主防线，黑名单是最后一道」比「我加了个黑名单」值钱得多。
8. **两个「看起来显然、实测不成立」的假设**（都是靠跑一遍才发现的）：① MCP 的同名工具会**覆盖**内置工具（`ToolRegistry.register` 就是字典赋值），所以线上跑的其实是 MCP 版 `read_file`、内置那份是死代码 —— 两个入口必须共用同一套沙箱函数，否则修一个另一个还漏着；② 「父进程设了环境变量，子进程自然能继承」是错的：mcp SDK 给子进程的是**过滤过的白名单** `get_default_environment()`，父进程里 `os.environ.setdefault("MCP_FS_ROOT", ...)` 完全无效，必须用 `StdioServerParameters(env=...)` 显式注入。两条都补了回归测试。
9. **为什么容器里强制 `--workers 1`**：不是保守取值，是硬约束 —— chroma 的 `PersistentClient` 同一目录同一时刻只允许一个进程打开，多 worker 会互相抢锁，现象是「记忆时有时无」且**日志里没有任何报错**。这个项目里的降级**全是静默的**：chroma 打不开会吞掉异常退回 JSON 后端、MCP 连不上只是工具凭空少几个 —— 所以部署后日志里那行 `agent ready, memory=ChromaVectorMemory, tools=[...]` 是关键自检点（`memory=VectorMemory` 就等于没连上）。
10. **SSE 部署后「不流式」的坑**：反代会缓冲响应，配置不对时前端页面看着完全正常，但逐 token 推送变成整段一次性蹦出来 —— 核心卖点没了却很难归因到反代配置。修法是 Caddy 的 `flush_interval -1`；验证手段是给每一行到达打时间戳，看是否分布在不同的秒上。
11. **为什么鉴权放 Caddy 而不是写进应用**：声明式、不用往业务代码里塞认证逻辑；cortex 端口不 publish、公网根本连不到，少一层暴露面；以后上域名 + HTTPS 只改 Caddyfile 几行、应用零改动。已知边界也要主动说：Basic over HTTP 是**明文传密码**，缓解手段是安全组把来源限制成自己的出口 IP；且它是单账号，长期记忆全局一份。
12. **参数校验的拦截率为什么是 87% 而不是 100%**（这题是主动送分）：23 条非法 + 9 条合法用例实测，拦截率 20/23、误杀率 0/9，非法参数下工具函数执行 0 次（校验确实发生在执行之前）。剩下 3 条漏放是同一个根因——`isinstance(True, int)` 在 Python 里为真，而 `_TYPE_MAP["integer"]` 就是 `int`，于是布尔值能从 integer / number 位混过类型检查并**真的执行**，数值工具会把 `True` 当 1 静默算错。**别只报自己设计用例的 100%**：那个数只是因为没测布尔；主动去探边界才把真实拦截率钉在 87%，修法是在 `_validate` 里对 `bool` 单独判一次（`isinstance(value, bool) and type_name != "boolean"` → 报错）。
13. **时间衰减到底有没有用**（用数据答，别空谈）：15 组「偏好变更」场景里新旧两条记忆结论相反、分别创建于 120 天前和 1 天前，问「现在是什么情况」。λ=0（纯余弦不衰减）时新记忆只排第一 26.7%——基本是撞的；λ=0.05 时 100%。这就是「记忆不是被硬删、而是随年龄淡出」这句话的实测支撑。
